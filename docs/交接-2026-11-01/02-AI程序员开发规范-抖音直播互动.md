# AI 程序员开发规范：抖音直播互动

交付对象：另一位程序员及其 AI 编码助手。配套范围和验收见 [项目现状与一周策划案](01-项目现状与一周策划案.md)。基准 `a486e36`，开工前必须重新核对实际分支及工作区；本文件是开发规范，不证明项目已接入平台或获得平台授权。

## 1. 开工流程

1. 阅读仓库 `AGENTS.md`（如有）、本交接和现有插件 README；执行 `git status --short --branch`、`git log -1 --oneline`、`git stash list`。不得覆盖、清理、重置他人的变更、存档、素材和 stash；任何需要迁移或删除先备份并另行确认。
2. 阅读 `BoundlessImmortality.uproject`、`Config/DefaultGame.ini`、`Source/BoundlessImmortality/LiveWeapons/LiveAudienceAdapterComponent.*`、`Source/BoundlessImmortality/XianTu/XianTuSubsystem.*`、`Source/BoundlessImmortality/Wuling/WulingPrototypeSubsystem.*`，沿调用链找实际运行入口。仓库里平台插件说明混有其他项目背景，配置和 SDK 能力必须根据本项目核验。
3. 先写简短任务拆分和验收用例，追踪一次事件的来源、身份、消费及回执，再做最小修改。AI 必须给出实际修改、命令及原始结果，不得编造平台 API、SDK 参数、测试通过或规则结论。不要猜测原生 SDK C ABI，不得绕过现有会话保护。
4. 测试前备份会修改的 `Saved/XianTu`、`Saved/CultivationPrototype` 和相关测试数据库；优先隔离临时目录。已有验证脚本可能消耗本地数据，先读脚本。不要把令牌、AppSecret、用户原始消息写入日志、提交或交接材料。

## 2. 先确认接入产品与官方资料

本项目为 UE 5.8 Win64 玩法。先让负责人核实抖音开放平台中的**实际玩法类型、AppId、权限和有效提案**；直播玩法、直播伴侣互动工具、抖音 SDK 面向第三方 App 是不同产品，协议不能混用。阅读官方 [创建直播玩法](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/introduction/zn/toybox-start)，根据后台核对评论、点赞、礼物、玩法客户端和可能的云启动能力、关键词及礼物配置；以当前官方 SDK、控制台及审核意见为准。直播伴侣互动工具的接口不能仅因字段相似就套用到本玩法。

确认是否有对应官方 SDK 版本、宿主可执行文件及其依赖、测试主播账号、直播伴侣/云启动权限和官方测试入口；缺任何一项，记录负责人及阻塞。绝不把 SDK 令牌放入源码、命令行日志或截图。本仓库 `DouyinLiveProvider` README 描述 Unity 宿主与管道，仅作为待验证的实现线索，检查实际文件与构建脚本是否齐备，不得假定已可打包。

## 3. 推荐的事件边界

平台 SDK/宿主 → `DouyinLiveProvider` → `ULiveInteractionSubsystem` → 游戏消费者 → 可见反馈/持久处理 → 根据实际平台契约上报处理结果。具体字段及 ACK 时机以本应用 SDK 文档和实测为准；不要把内部 `Deliver*` 返回 true、游戏线程排队成功、或 SDK void 调用成功等同平台持久确认。

- Provider 负责授权会话、真实平台消息解码、线程切换、消息重投及映射；游戏只处理类型化事件。事件必须验证当前平台、应用、房间、会话代次及非空身份；使用 `GetScopedUserId`，不以昵称作为持久主键。
- 同一平台消息使用原始 `MessageId`；所有消费者共享清楚的处理归属和结果。现在 `ULiveAudienceAdapterComponent` 与 `UXianTuSubsystem` 都订阅评论；`加入` 与 `助力` 必须分别追踪，避免一个消费者提前 ACK 另一个消费者尚未完成的消息。检查过滤、订阅生命周期、会话切换与消费方尚未就绪的情况。
- 渡劫助力属于免费玩法事件，按现有规则做用户级去重；同一消息的去重和同一用户的助力限制是两件事。不得信任客户端上报的他人身份和服务端应决定的经济结果。
- 正式/本地模拟/平台测试数据必须隔离。`WulingPrototypeSubsystem` 显式要求 `-WulingPrototype -GWLocalTest`，其本地 SQLite HTTP 服务只用于封闭原型；不得通过移除检查把它直接暴露公网或伪装为生产。
- 现有礼物处理在 `LiveAudienceAdapterComponent.cpp` 对非本地测试礼物采取隔离；Provider README 中对测试礼物的说明与此不等价。不得为了联调删除隔离、把礼物转成评论或把测试权益写入正式存档；先按本项目官方要求设计并在隔离环境验证。
- 真正的付费功能需要权威身份、持久事件账本、业务事务、幂等、重启恢复、补偿和可追踪的处理状态。内存去重窗口、本地 JSON 或“已经播放动画”均不足以证明跨崩溃履约；本周不启用正式付费。

## 4. 实施与验证规范

保持 UE C++ 生命周期安全，游戏对象和 UI 操作在游戏线程；异步回调使用安全引用，退出与会话变更时解绑。保持原有玩法、资产、中文文案和存档兼容，新增配置缺失时明确显示未就绪，不静默退回正式模式的模拟数据。官方 ID 按本项目控制台核验；仓库中的名称或加密 ID 只是已有配置，不能证明已获授权。不要自造礼物、金额、发奖或排行榜 API。

至少验证：正常加入与助力；同人重发、同消息重投、不同人、50 人上限；主播自身、空身份、旧房间/旧代次、断线重连；无消费者/失败/队列满/回执失败。记录测试使用的是模拟事件还是官方事件。除单元测试外，至少一次本地 Windows PIE 完整实操，提供可复现步骤和截图；真实平台需单列账号环境与证据，敏感内容打码。缺失 SDK/账号则明确 `blocked`，不能改为“通过”。

测试优先沿用项目已有自动化。服务测试命令参考 `python -m unittest discover -s Tools/CultivationService/tests -v`，但它仅验证本机服务，不能证明 UE 或平台；完整 PIE 与构建按本机可用引擎和现有脚本执行并记录。测试失败、未运行和受限要如实列出。

## 5. AI 交付模板

```text
基准：分支 / 提交 / 开始时工作区状态
目标与不在范围：
证据：源码路径和行号；官方资料链接及账号权限情况
改动：文件、行为、兼容性和存档影响
测试：环境、完整命令、结果、截图位置；模拟/PIE/真实平台分别列出
风险与未完成：包括平台阻塞、回执语义和付费可靠性
后续：负责人、前置条件、具体验收标准
```

AI 应先读已有实现再动手；遇到权限、真实礼物规则、不可逆迁移或现有实现与策划冲突时保留证据，交给负责人决策。不得以自动生成文档或测试数量替代真实运行结果。

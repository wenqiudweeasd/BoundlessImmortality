交给一位熟悉 UE C++ 的程序员，假设一周业余时间 **12–15 小时**，目标做出可复现的“观众加入剑灵 → 渡劫期间发送助力 → 主播看到反馈”的免费互动闭环及平台联调准备。验收默认本地模拟；只有具备本项目的平台资质、测试账号和有效启动方式时，才增加真实平台证据。一个人、一周不能同时承诺生产服务器、付费可靠履约、平台审核通过及全部缺失内容。

## 一周任务卡

**体验规则（建议，沿用现有逻辑）**：观众输入“加入”参与，生成或恢复其剑灵；有效渡劫阶段发送含“助力”的评论可助力一次，已助力重复发送不重复增加。已有实现是每名不同用户 1 个百分点、最多 50 名有效助力，具体概率及状态以 `TribulationProbability` 和现有代码为准；非有效阶段不增加概率，并显示合理反馈。不同房间、不同用户不得互相借用身份或助力，主播自身不计入。不要改变现有数值、礼物效果和存档。

| 任务 | 预计 | 完成标准 |
|---|---:|---|
| T1 基线与权限盘点 | 1–2h | 记录分支、改动、UE 版本、启动方式、现有测试；检查本项目平台资质、官方 SDK 与宿主是否存在，记录缺项。 |
| T2 免费事件边界 | 3–4h | 追踪加入/助力从来源校验到玩法及 ACK 的实际路径；修复当前会话、用户非空、重复/失效事件问题，保证仅对真实处理结果回执。 |
| T3 玩家反馈 | 1–2h | 在现有 HUD/通知链清楚展示加入、成功助力、重复或阶段不符；避免每条无关评论刷屏。 |
| T4 验证 | 3–4h | 自动化覆盖正常/重复/旧会话/不同用户与房间；本地 PIE 手工走完整流程，记录步骤与截图。平台条件具备时另测真实评论；没条件写明 blocked。 |
| T5 交接与预留 | 2–3h | 更新接入清单、缺陷与后续付费设计，提交源码和可复现证据；确认不含密钥与用户敏感原文。 |

若只剩 8 小时，依次保留 T1、T2 和 T4 中的核心用例，T3 使用现有提示，T5 简化；真实平台阻塞不能由本地模拟替代。若发现需要新建后端或重构 ACK 才能安全完成，应停在免费模拟闭环并记录剩余设计，不临时扩大范围。

## 验收矩阵

1. 新观众“加入”只建立一个对应身份，重发不生成重复剑灵；退出/重新进入后状态行为有明确记录。
2. 渡劫准备期、正式期、结束后各发“助力”；只有允许阶段改变概率。一个用户重复发、两个用户各发、主播发送、超过 50 人各有可观察结果；实际阈值以现有规则核对。
3. 空用户、旧会话、切换房间后的旧事件不能改变当前房间；重连后新事件可正常处理。模拟与正式身份隔离。
4. 对同一 `MessageId` 重投不会重复生效；断线、消费方未就绪、队列满和 ACK 失败不伪报成功。若现有实现无法覆盖某项，记为缺陷而不是通过。
5. 测试报告列出构建/测试命令、版本、日期、结果、未测项目；PIE、正式 SDK、打包、真机/云启动、平台审核分别标注。平台测试礼物不进入正式存档或计费权益，最终处理遵循当前实际 SDK 文档与提案。
